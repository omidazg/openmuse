# ظرفیت، سرور دوم و دسترس‌پذیری بالا

این سند برای زمانی است که یک سرور دیگر کافی نیست: یا بار بیشتر شده است، یا قطعی یک دیتاسنتر
دیگر پذیرفتنی نیست. راه‌اندازی فعلی در [`deploy/arvan/README.fa.md`](../deploy/arvan/README.fa.md)
آمده است.

## ۱. وضعیت فعلی و ظرفیت

سرور فعلی: ابرآروان تهران (بامداد، `ir-thr-ba1`)، ۲ vCPU، ۴ گیگابایت RAM، ۲ گیگابایت swap، دیسک
۲۳ گیگابایتی.

| سرویس | سقف حافظه | توضیح |
| --- | --- | --- |
| `app` | ۱ گیگابایت | API و وب؛ بیشتر منتظر پاسخ مدل (متیس) است و CPU کمی می‌خواهد |
| `worker` | ۱ گیگابایت | کارهای پس‌زمینه |
| `browser-worker` | ۲ گیگابایت | Chromium؛ هر نشست مرورگر حدود ۳۰۰ تا ۵۰۰ مگابایت |
| `postgres` | بدون سقف | با داده‌های فعلی چند صد مگابایت |
| `backup` / `monitor` / `caddy` | ۲۵۶ / ۶۴ مگابایت / کم | |

برآورد تقریبی: چند ده کاربر هم‌زمانِ گفت‌وگو و یک یا دو نشست مرورگر هم‌زمان. گلوگاه اول معمولاً
**حافظه** (مرورگر و build وب هنگام استقرار) و **دیسک** است، نه CPU.

نشانه‌های نیاز به ارتقا:

- استفادهٔ مداوم از swap (`free -m`) یا کانتینرهایی که با کمبود حافظه بسته شده‌اند:
  `docker inspect -f '{{.Name}} {{.State.OOMKilled}}' $(docker ps -aq)`
- بار CPU بیش از ۷۰٪ برای مدت طولانی (`docker stats`)؛
- هشدار دیسک از `monitor` حتی پس از پاک‌سازی (بخش ۱۳ راهنمای استقرار)؛
- کندی پاسخ `/api/health` یا قطع استریم گفت‌وگو در ساعت‌های شلوغ.

**گام اول همیشه ارتقای عمودی است:** از پنل ابرآروان اندازهٔ سرور را به ۴ vCPU و ۸ گیگابایت و دیسک
را بزرگ‌تر کنید. این کار چند دقیقه قطعی دارد، ولی هیچ تغییری در معماری نمی‌خواهد. سرور دوم را
برای **دسترس‌پذیری** اضافه کنید، نه برای ظرفیت.

## ۲. چه زمانی سرور دوم؟

- وقتی قطعی چندساعتهٔ یک دیتاسنتر (بامداد) برای کاربران پذیرفتنی نیست؛
- وقتی می‌خواهید سرور اصلی را بدون قطعی به‌روز یا بازسازی کنید؛
- وقتی از بزرگ‌ترین اندازهٔ سرور هم فراتر رفته‌اید (در این حالت معماری فعال-فعال لازم است، بخش ۵).

منطقه‌های مناسب برای سرور دوم: تهران سیمین (`ir-thr-si1`) یا فروغ (`ir-thr-fr1`)، یا برای
جداسازی جغرافیایی بیشتر، تبریز شهریار (`ir-tbz-sh1`). هزینهٔ یک سرور هم‌اندازه حدود ۱٬۹۶۶٬۲۰۰
تومان در ماه است.

## ۳. معماری پیشنهادی: آماده‌به‌کار گرم (Active-Passive)

ساده‌ترین حالتی که قطعی دیتاسنتر را پوشش می‌دهد:

```
            DNS / متعادل‌کنندهٔ بار CDN ابرآروان
             │ (سلامت: /api/health)
     ┌───────┴────────┐
 سرور A (بامداد)    سرور B (سیمین)
 app, worker,       app و worker متوقف،
 browser, caddy     caddy و browser آماده
 postgres (اصلی) ──► postgres (replica، فقط‌خواندنی)
     │                    │
     └──── پشتیبان‌ها در فضای ابری ابرآروان (پیشوند جدا) ────┘
```

- **پایگاه داده:** replica استریمی PostgreSQL روی سرور B (بخش ۴)، یا پایگاه دادهٔ مدیریت‌شدهٔ
  ابرآروان (DBaaS) اگر برای PostgreSQL ۱۷ در حساب شما فعال است؛ در آن صورت هر دو سرور به همان
  نشانی وصل می‌شوند و بخش ۴ لازم نیست.
- **فایل‌ها:** `app-data` (کلید امضای نشست و PDFها) روی دیسک محلی است. کلید
  `session-signing-key` و `.env` باید روی هر دو سرور **یکسان** باشند. PDFها را با بازگردانی آخرین
  بایگانی `app-data` (بخش ۹ راهنمای استقرار) یا یک همگام‌سازی دوره‌ای با rclone به سرور B برسانید.
  برای فعال-فعال واقعی، ذخیرهٔ PDFها باید به فضای ابری S3 منتقل شود (تغییر کد در `files.ts`).
- **پشتیبان:** سرویس `backup` فقط روی سرور اصلی فعال باشد (`BACKUP_ENABLED=0` روی B). اگر
  روی هر دو فعال است، `BACKUP_S3_PREFIX` را متفاوت بگذارید.
- **worker:** فقط یک `worker` فعال باشد؛ اجرای هم‌زمان دو worker روی یک پایگاه داده هنوز آزموده
  نشده است.

## ۴. replica استریمی PostgreSQL

روی سرور A (اصلی):

1. کاربر replication:
   ```bash
   sudo docker compose exec postgres psql -U openmuse -c \
     "CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD '<openssl rand -hex 24>';"
   ```
2. در `compose.yaml` برای `postgres` تنظیمات WAL را اضافه کنید:
   ```yaml
   command: ["postgres", "-c", "wal_level=replica", "-c", "max_wal_senders=5",
             "-c", "wal_keep_size=1GB", "-c", "hot_standby=on"]
   ports: ["<IP-خصوصی-یا-عمومی-A>:5432:5432"]
   ```
   و به `pg_hba.conf` (داخل volume `pgdata`) فقط IP سرور B را اضافه کنید:
   `host replication replicator <IP-B>/32 scram-sha-256`
3. در ufw فقط به IP سرور B اجازه دهید: `ufw allow from <IP-B> to any port 5432 proto tcp`.
   شبکهٔ خصوصی ابرآروان بین منطقه‌ها مشترک نیست؛ برای ترافیک بین دو منطقه یک تونل WireGuard
   بسازید یا دست‌کم TLS پایگاه داده (`ssl=on`) را فعال کنید.

روی سرور B:

```bash
cd /opt/openmuse/deploy/arvan
sudo docker compose stop postgres app worker
sudo docker run --rm -it -v openmuse_pgdata:/var/lib/postgresql/data \
  docker.arvancloud.ir/library/postgres:17-alpine sh -c \
  'rm -rf /var/lib/postgresql/data/* && pg_basebackup -h <IP-A> -U replicator \
     -D /var/lib/postgresql/data -R -X stream -P && chown -R postgres:postgres /var/lib/postgresql/data'
sudo docker compose up -d postgres caddy browser-worker
```

`-R` فایل `standby.signal` و تنظیم اتصال را می‌سازد و replica فقط‌خواندنی بالا می‌آید. بررسی
روی A: `SELECT client_addr, state, replay_lag FROM pg_stat_replication;`

## ۵. متعادل‌کنندهٔ بار و جابه‌جایی DNS

**روش الف، متعادل‌کنندهٔ بار CDN ابرآروان:** دامنه باید روی CDN ابرآروان با پروکسی روشن باشد.
در پنل ← CDN ← «متعادل‌کنندهٔ بار» یک استخر مبدأ با سرور A (اولویت اول) و سرور B (پشتیبان)
بسازید و بررسی سلامت را روی مسیر `/api/health` با کد ۲۰۰ تنظیم کنید. نکات بخش ۵ راهنمای استقرار
(اتصال HTTPS به مبدأ، کش‌نکردن `/api/*` و بافرنکردن SSE در `/api/copilotkit`) این‌جا هم لازم‌اند.
Caddy روی هر دو سرور باید گواهی معتبر داشته باشد؛ پیش از روشن‌کردن پروکسی، گواهی هر سرور را با
خاموش‌بودن پروکسی و رکورد A موقت بگیرید، یا اتصال به مبدأ را روی HTTPS بدون اعتبارسنجی بگذارید.

**روش ب، بدون CDN:** TTL رکورد A را ۶۰ ثانیه بگذارید و هنگام قطعی، رکورد را از پنل یا API
ابرآروان به IP سرور B تغییر دهید. ساده‌تر است، ولی جابه‌جایی دستی است.

در هر دو روش `DOMAIN` روی هر دو سرور یکسان است و `set-domain.sh` لازم نیست.

## ۶. دستورالعمل جابه‌جایی (Failover)

1. مطمئن شوید سرور A واقعاً از دسترس خارج است (هشدار `monitor` و `smoke.sh` از بیرون).
2. روی B، replica را به اصلی تبدیل کنید:
   `sudo docker compose exec postgres psql -U openmuse -c "SELECT pg_promote();"`
3. روی B: `sudo docker compose up -d app worker` و در صورت نیاز `BACKUP_ENABLED=1`.
4. متعادل‌کنندهٔ بار خودکار جابه‌جا می‌شود؛ در روش ب رکورد A را تغییر دهید.
5. `./deploy/arvan/smoke.sh https://<DOMAIN>` از سیستم خودتان.
6. پس از بازگشت A، آن را با `pg_basebackup` (بخش ۴) replica سرور B کنید. هرگز دو سرور را هم‌زمان
   به‌عنوان اصلی روشن نگذارید.

## ۷. فهرست بررسی پیش از راه‌اندازی سرور دوم

- [ ] پشتیبان خارج از سرور (فضای ابری ابرآروان) فعال و بازگردانی یک‌بار آزموده شده است.
- [ ] `.env` و `session-signing-key` روی هر دو سرور یکسان است.
- [ ] replica یا DBaaS با تأخیر کم (`replay_lag`) کار می‌کند.
- [ ] `monitor` روی هر دو سرور با کانال هشدار مشترک و `ALERT_NAME` متفاوت فعال است.
- [ ] دستورالعمل بخش ۶ یک‌بار در زمان کم‌بار تمرین شده است.
